# 주문·결제·권한 사후 점검

프로젝트 종료 후(2026-10-16~17) `ajou-order-web`, `ajou-order-server`의 주문·결제·권한 흐름을 코드 리뷰와 배포 화면 확인으로 다시 점검한 기록입니다.
개발 당시에 이미 알고 해결한 문제가 아니라, **종료 후 추가로 발견한 문제**를 정리한 문서입니다.

## 점검 범위와 방법

- 대상: 두 저장소의 `main` 브랜치, 배포된 웹 화면, 운영 Supabase의 RLS 정책과 테이블 권한
- 방법: 코드 확인, 로그아웃 브라우저에서 화면 접근과 장바구니 조작, Supabase 대시보드에서 정책·권한 **읽기 전용 조회**
- 하지 않은 것: 실제 결제, 주문 생성, 운영 데이터 수정, 익명 쓰기 요청 시도

## 1. 발견한 문제

| 문제 | 확인 방법 | 위험 |
|---|---|---|
| 로그인 없이 `/admin` 화면 접근 가능 | 로그아웃 상태 배포 화면에서 재현 | 주문 정보 노출 |
| `orders` 테이블 조회가 누구에게나 허용됨 (공개 anon 키로 건수 조회 성공) | 요청 재현 + 정책 조회 | 주문 정보 노출 |
| `orders` INSERT·UPDATE, `cafes` UPDATE가 익명에게 허용되는 구성, `menus`는 RLS 꺼짐 | 정책·권한 조회 (실제 쓰기는 미시도) | 주문·가격·영업 상태 변조 가능 구성 |
| 토스 결제 성공 페이지가 결제 승인 API 호출과 금액 대조 없이 주문을 저장 | 코드 확인 (결제 미수행) | 결제하지 않은 주문 생성, 금액 불일치 |
| 주문 저장 전에 결제 키·주문 ID 중복 검사 없음 | 코드 확인 | 새로고침 시 중복 주문 가능성 (실제 재현 미수행) |
| 주문번호를 "마지막 번호 조회 후 +1"로 발급 | 코드 확인 | 동시 주문 시 번호 충돌 가능성 (실제 재현 미수행) |
| 서버 주문 API가 사용자 ID·품목·총액을 요청 본문 그대로 저장 | 코드 확인 | 클라이언트 값 신뢰 |
| 주문 없이 `/order/complete`에 접근하면 예시 주문이 "주문 완료"로 표시됨 | 배포 화면에서 재현 | 사용자 혼동 |
| 토스 외 결제 수단은 1.5초 대기 후 주문을 만드는 시뮬레이션 | 코드 확인 | 실제 결제로 오해될 표현 |

정상 동작도 한 건 확인했습니다. 카페라떼(1,700원)에 샷 추가(300원)를 선택하면 메뉴 화면과 장바구니가 모두 2,000원으로 일치했습니다. 이 확인은 메뉴 1개·옵션 1개·수량 1개에 한정됩니다.

## 2. 적용한 조치

### 2026-10-16: 1단계 (노출과 쓰기 경로 차단)

1. 웹: 주문·완료·관리자·결제 성공 화면을 점검 안내 페이지로 교체하고 장바구니 주문 버튼을 비활성화했습니다 ([웹 PR #2](https://github.com/juunghaa/ajou-order-web/pull/2)).
2. 서버: 새 주문과 카페 수정 API를 503으로 중지했습니다 ([서버 PR #1](https://github.com/juunghaa/ajou-order-server/pull/1)).
3. Supabase: [권한 제한 SQL](https://github.com/juunghaa/ajou-order-server/blob/main/supabase/migrations/20261016_restrict_public_access.sql)을 운영에 실행했습니다 (저장소 병합과 별도로 수동 실행).

적용 후 읽기 전용 조회 결과:

| 테이블 | RLS | anon 조회 | anon 쓰기 | authenticated 조회 | authenticated 쓰기 |
|---|---|---|---|---|---|
| `cafes` | 켜짐 | 허용 | 거부 | 허용 | 거부 |
| `menus` | 켜짐 | 허용 | 거부 | 허용 | 거부 |
| `orders` | 켜짐 | 거부 | 거부 | 본인 주문만 | 거부 |

### 2026-10-17: 메뉴·견적 기반 작업

- 서버에 메뉴 85개 스냅샷, 카페별 메뉴 조회 API, **읽기 전용** 주문 견적 API를 추가했습니다 ([서버 PR #2](https://github.com/juunghaa/ajou-order-server/pull/2)). 견적은 클라이언트가 보낸 가격을 쓰지 않고 서버 목록의 가격으로 계산하며, 잘못된 메뉴·옵션·수량은 거부합니다. 서버 테스트 5개가 통과합니다.
- 웹 메뉴 화면과 AI 추천 모달이 서버 메뉴 목록을 사용하도록 바꿨습니다 ([웹 PR #3](https://github.com/juunghaa/ajou-order-web/pull/3)).

### 문서·코드 정리

- README를 실제 코드에 맞게 수정했습니다 (결제 승인 미구현, 시뮬레이션 결제 수단, 사용 중인 AI 모델, 존재하지 않는 엔드포인트와 기능 설명 제거).
- 사용하지 않던 Firebase 설정 파일과 의존성, 실패하던 CRA 기본 테스트, 미사용 `logo.svg`를 삭제했습니다.

## 3. 남은 한계

의도적으로 하지 않은 작업입니다. 이 프로젝트는 서비스 재개가 아니라 **문제를 찾고 위험한 경로를 닫는 것**까지를 범위로 했습니다.

- **주문·결제·관리자 기능은 중지 상태입니다.** 재개하려면 아래가 모두 필요합니다.
  - 인증된 서버 주문 경로
  - 서버의 토스 결제 승인과 금액 검증
  - 결제 키·주문 ID 고유 제약
  - 원자적 주문번호 발급 (같은 카페·같은 날짜 동시 주문 테스트 포함)
  - 관리자 권한 검사
- 중복 주문과 번호 충돌은 **실제 요청으로 재현하지 않았습니다.** 재개 전에 DB 고유 제약과 동시 요청 결과를 확인해야 합니다.
- 조치 후 익명 쓰기 거부와 로그인 사용자의 주문 내역 조회는 **실제 요청으로 검증하지 않았습니다.** 권한·정책 조회와 공개 화면 확인까지만 했습니다.
- 메뉴 85개는 웹(`menuData.js`)과 서버(`menuCatalog.json`)에 이중으로 있고, 운영 DB `menus` 테이블은 비어 있습니다. 단일 원천은 정하지 않았습니다.
- 건의사항·메뉴 추천 기능(`feedbacks`, `menu_recommendations`)의 RLS는 이번 점검 범위에 포함하지 않았습니다. 해당 POST는 입력 검증과 인증이 없습니다.
- AI 추천 API에는 인증과 호출 제한이 없고, 서버 CORS는 전체 허용입니다.
- 웹 `package-lock.json`이 `package.json`과 맞지 않아 `npm ci`가 실패합니다 (`npm install`은 동작).
